# LinkedIn: when-a-spreadsheet-should-become-a-database

## Post 1: native text

A spreadsheet should become a database when several people depend on it and the data has to stay correct while they all change it.

Size is rarely the reason. Excel allows over a million rows per sheet, and most business spreadsheets get into trouble long before that.

The signs are usually about people:

• The same customer appears in three tabs, and they don't agree.
• There's more than one file with "final" in the name.
• A sorted column broke the formulas and nobody knows what changed.
• You can't tell who edited a number, or when.
• Only one person understands how it works.

A database fixes these with rules. A status can only be one of a fixed list. An order has to belong to a real customer. A customer is stored once, so changing an address updates every order. The database enforces this itself, so a rushed Friday edit can't break it quietly.

Spreadsheets are still the right tool when one person owns the sheet, when it's for analysis, or when the process behind it changes every week.

When it is time to move, start with the data model. Screens can be redesigned in a week, but a database with years of records in it is much harder to restructure. Then import, run both side by side, and retire the spreadsheet once the team trusts the new system.

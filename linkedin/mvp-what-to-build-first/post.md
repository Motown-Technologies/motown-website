# LinkedIn: mvp-what-to-build-first

## Post 1: native text

A customer asked for one feature. A competitor has another. Each one makes sense, and your launch date moves every time the list grows.

A first version only has to answer one question: will people do this thing, and pay for it, if you make it easy enough?

So map the journey from the user's starting problem to the moment they get value. For each proposed feature, ask whether that journey works without it. If it does, the feature waits.

The part people skip is writing down why. "Later" next to a feature doesn't settle the argument that put it there, and it'll come back at the next meeting. Note who needs it, what they'd do without it and what evidence would bring it back. Then people can point to the decision instead of reopening it.

A shorter list leaves room to make the one journey work properly: sign-in that fits, storage you can trust, a way to roll back a bad release. Payments go in if paying is part of the test.

When a new request turns up mid-build, hold it against the journey. If it has to go in, say what it costs: the date, the budget or another feature.

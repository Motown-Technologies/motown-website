Partway through a sale or an investment, the buyer's reviewers ask for a list of every open source package your software uses and the license on each. A typical web application pulls in hundreds. Most of those licenses ask almost nothing. A few can require you to publish your own source code, and those are the ones to find before someone else does.

This is a general explanation from a software team, not legal advice. When a license question affects a sale, a raise or a contract, ask a lawyer who works on software licensing.

## Most licenses only want the notice

Permissive licenses let you use, change and sell the code in your own closed commercial product, as long as you keep the original copyright and license notice. The two you'll see most are MIT and Apache 2.0. According to [choosealicense.com](https://choosealicense.com/licenses/), a guide maintained by GitHub, neither requires you to share your own source code. Apache 2.0 also includes an explicit patent grant, which some companies' lawyers prefer.

## The GPL asks you to share alike

Copyleft licenses let you use and change the code too, but if you distribute software built on it, you have to make the source available under the same license. The best known is the GNU General Public License (GPL). Hand someone a copy, as a desktop program or a device with the code inside, and its conditions apply. Code that only runs on your own servers, reached through a browser, generally doesn't count as distribution under the standard GPL.

There are milder versions. The LGPL lets a separate program use a library through its interfaces without the whole program falling under the license, and the Mozilla Public License applies its conditions file by file.

## In a web app, check the AGPL first

The GNU Affero General Public License (AGPL) closes the gap the GPL leaves for hosted software. Choosealicense.com summarizes it as treating network use as distribution. Modify AGPL code, let people use it over a network, and you have to make your modified source available to them. If you plan to keep your product's source private, this is the license that needs a decision.

Source-available licenses such as the SSPL and the Business Source License publish the code but often restrict commercial hosting. The Open Source Initiative has said that [the SSPL is not an open source license](https://opensource.org/blog/the-sspl-is-not-an-open-source-license), and the BSL isn't on its [approved list](https://opensource.org/licenses) either. They may still be fine for your use, but read the actual terms.

## When it starts to matter

Day to day, licenses rarely cause trouble. They come up in a sale or raise, in a large customer's procurement questionnaire, and once you ship software to customers. Say a clinic commissions a patient portal and later wants to license it to other clinics. Code that was harmless inside one private system now ships to other organizations, and the license list suddenly matters.

Reviewers will also ask whether contractor agreements assign the code to your company. We cover the rest of that review in [what technical due diligence checks](/blog/technical-due-diligence-explained).

## One request for this week

Ask your developers for a dependency list with each license, generated by a tool rather than written by hand. Agree a short rule: permissive licenses are fine, and copyleft and source-available ones get reviewed before they're added. Doing it now leaves time to replace a component or ask a lawyer, which a hurried sale doesn't.
